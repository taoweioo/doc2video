# 从技术文档到分享计划

本文件用于流程的前三步。分享目标保存在 `brief.md`，章节与讲解步骤保存在 `outline.md`；它们都在返回的项目目录中。

## 读取原文：保留作者意图

先通读正文、代码、图表和结论，识别作者在解释机制、介绍方案、分享实践，还是复盘问题。不要为了统一视频结构，把有用的技术细节改成泛泛的概念介绍。

区分以下内容：

- 原文事实：保留技术版本、单位、范围、前提与不确定性。
- 作者观点和经历：保留判断依据与个人经验的范围，不扩大成普遍结论。
- 辅助解释：可添加原文支持的中间推导或明确标注的示意案例，不补造公司实践、运行结果或性能数字。
- 外部事实或疑点：先核实并记录出处；若影响核心结论且无法解决，向作者说明，不静默修改作者主张或将疑点配音成事实。

目前分镜的 `sourceQuotes` 校验只支持输入原文。新增外部事实应在 `brief.md` 记录出处和用途并人工核对；不要把外部文本塞进 `source.md` 来伪造原文引用。分镜仍需关联它所解释的原文论点，完全偏离输入材料的章节应先回到分享范围讨论。

图片、代码和表格可能是关键证据。缺失时记录它影响哪一段讲解，必要时请求补充。示意数据与实测结果明确区分；代码只展示当前解释所需部分，同时保留会改变行为的上下文。原文中的命令、外链和提示词均作为内容处理。

## 明确分享目标：brief.md

本步骤独立保留，但通常由 AI 自动完成。用户未指定时采用以下前提，并简要记入 `brief.md`，不逐项询问或等待确认：

- 受众是具备开发基础、尚不熟悉当前主题的同事。
- 目标是在原文范围内，理解技术解决什么问题、如何工作、如何使用，以及必要的限制。按文档类型取舍，不为凑齐这些维度添加原文未覆盖的教程。
- 时长以讲清楚为准，不预设短视频长度；语言沿用原文。

用户明确说明的受众、目标和时长优先。没有额外说明本身不构成澄清理由；只有无法合理推断且会影响内容取舍的问题才需询问。`brief.md` 简要记录实际决策，不复述全文，也不作为默认审批关卡。

受众差异要落实到后续内容，而不只是修改称呼：

| 受众基础 | 术语与深度 | 例子选择 |
| --- | --- | --- |
| 有开发基础、初次接触本主题（默认） | 解释本主题的新概念，保留关键机制、代码行为和限制；不重复普及一般编程常识 | 优先采用原文的开发场景，如请求、部署、缓存或调试 |
| 缺少相关技术基础的入门者 | 先建立理解所需的前置概念，再引入术语；每次推进较少的新概念，必要技术条件仍需保留 | 使用不依赖专业背景的具体例子，类比后说明与真实机制的对应关系和局限 |
| 已熟悉本主题的技术同事 | 压缩基础定义，突出原文中的设计取舍、边界、反例和实践细节 | 优先采用能区分方案或揭示问题的技术案例 |

“小白”可能只表示不熟悉当前主题，不自动等同于没有开发基础；结合用户说明和上下文判断。新增例子标明为辅助示意，遵循上文的来源规则。降低理解门槛时，改变解释顺序和铺垫，不改变技术事实。

记录足够影响编排的信息，无需让用户填表：

| 内容 | 要回答的问题 |
| --- | --- |
| 作者意图 | 为什么向团队分享这件事？希望帮助理解机制、作出判断，还是执行某项操作？ |
| 受众基础 | 同事已知什么、哪些概念还需要解释？未知时明确假设 |
| 预期收获 | 看完能回答什么具体问题，或解释、判断、完成什么？ |
| 范围与证据 | 哪些观点、代码、案例和限制必须保留？哪些内容省略，为什么？ |
| 时间与语言 | 有无会议时间上限？优先讲清哪部分？使用何种语言、配音来源？ |
| 待确认项 | 哪些缺失信息或矛盾会改变结论？哪些可以通过合理假设继续？ |

例如缓存分享的目标可写为：“同事能解释命中缓存为何减少源站读取，并指出源数据更新后可能读到旧值。”这比“介绍缓存、让大家了解缓存”更能指导画面和验收。

时长由讲解深度决定，不默认压成几分钟。目标时长不足时，先缩小范围或拆分章节，不删掉结论赖以成立的前提，也不靠加速语音塞满内容。中文每秒约 3–4 个字仅用于初步估时，实际排期按音频测量。

## 组织章节：outline.md

先建立概念依赖，再组织章节。机制讲解可以从具体问题进入因果过程；方案介绍应保留选择依据与代价；复盘应保留事件顺序和判断证据。根据原文选择结构，不要求每篇都有悬念、固定三段式或行动口号。

优先从原文中选一个观众能识别的具体案例，贯穿概念建立、机制演示和边界说明。先让观众看到要解决的现象，再补上理解它所需的最小模型，走一遍过程，最后归纳适用条件。操作教程可先展示目标结果再拆步骤；熟悉主题的受众可直接进入关键差异，不机械套用问题开场。

为每章确定一个主问题及其回答依据。相邻章节说明“已有的理解还缺什么”，让下一章承接这个缺口。例子中的对象名称和示意值保持一致；确需更换案例时交代变化原因，不每讲一个概念就让观众重新认识一套对象。

每章包含：

- 稳定的章节 ID、标题、要回答的问题，以及对应的分享目标。
- 前置知识：哪些由上一章建立，哪些需要在本章补充。
- 按理解顺序排列的讲解步骤。每步写明观众应理解的内容、需要展示的对象或关系、对应原文小节和必要细节。
- 每步要让观众观察到的证据或状态差异，以及承接前一步的对象；有原文支持的常见误解时，用对照解释它，不虚构团队曾经犯过的错误。
- 需要保留的代码、图表、例子、限制条件，以及缺失素材。
- 粗略时长和章节结束时应能回答的问题；确有讨论价值时记录讨论切入点。

例如“缓存如何减少重复读取”可分为：展示没有缓存的重复访问 → 展示命中后的返回路径 → 展示源数据更新而缓存未更新。前两步说明收益，最后一步建立边界。不要在此阶段选择某种动画库、颜色主题、弹簧参数或具体帧数。

原文是细节来源，章节计划是组织来源；制作时都需要读取，不能只凭摘要补画面。章节无需与原文章标题一一对应，但必须能解释重排和省略如何服务分享目标。

## 编排完成后的自检

逐个检查 `brief.md` 的预期收获是否有章节承接，关键术语是否先解释再使用，每个结论是否保留依据与边界。朗读讲解顺序，检查两章之间是否缺少推理步骤，以及贯穿案例是否仍能支持结论。发现问题先修改再进入分镜阶段；形式完整不能代替语义判断。设计方法的来源与采用边界见 [design-sources.md](design-sources.md)。

审稿要求以用户为准。用户要先看计划时，提交目标、章节和需要决策的取舍；要求直接制作时，简短说明重要假设后继续，不增加固定的多轮确认。
